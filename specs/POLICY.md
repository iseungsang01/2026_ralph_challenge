# POLICY — Edge Case 판정집

이 문서는 edge case 기반으로 설계됐다. 형식: **상황 → 판정 → 이유**.
PRD와 충돌하면 POLICY가 우선한다. 여기 없는 상황은 §25 메타 규칙을 따른다.

## A. 분류·중복

**§1. 한 논문이 여러 섹터에 걸친다 (CLIP, Stable Diffusion, ViT…)**
→ canonical 노드 1개만 만들고, `sector`는 그 연구가 주로 바꾼 연구 커뮤니티의 섹터로, 나머지는 `also_in`에 넣는다. 상세 페이지는 항상 1개다.
→ 이유: 중복 상세는 내용이 갈라지고 유지가 깨진다. 노출은 렌더링이 해결한다.
난제 판정표(고정): CLIP→multimodal(also: vision), DDPM/Stable Diffusion/DALL·E→generative, ViT→vision, Whisper→speech_audio, AlphaGo→rl_games, AlphaFold→ai4science, Codex→code_agents, GPT-4→nlp_llm, NeRF→generative.

**§2. 같은 항목을 두 섹터 데이터 파일에 넣고 싶다**
→ 금지. 데이터에는 한 번만 존재한다(id 전역 유일, validator 강제). `also_in` 섹터의 flow chart에는 렌더러가 공동 배지를 달아 표시한다.
→ 이유: 단일 진실 원천(single source of truth).

**§3. 섹터 판정이 정말 50/50이다**
→ 현재 노드 수가 더 적은 섹터에 배정하고, `uncertainty`에 판단 근거를 1줄 남긴다.
→ 이유: 커버리지 균형 + 판단 추적 가능성.

## B. 계보 (flow chart 엣지)

**§4. "영감을 받았다" 수준의 관계도 엣지로 그리고 싶다 (예: GPT-3 → 거의 모든 후속 연구)**
→ 금지. `evolves_from`은 **직접 계승만**: (a) 같은 패밀리의 후속 버전, (b) 논문이 명시적으로 직접 기반 삼은 선행 연구. 넓은 영향 관계는 `impact` 텍스트로 서술한다.
→ 이유: 전부 이으면 flow chart가 스파게티가 되어 "발전 과정이 보인다"는 목적 자체가 죽는다.

**§5. 엣지가 시간을 거스르거나 순환한다**
→ 금지. 엣지는 반드시 과거→미래(선행 노드의 year ≤ 자신의 year). 순환은 validator가 거부한다.
→ 이유: 시계열 계보도의 정의.

**§6. 계승 대상이 다른 섹터에 있다 (ViT(vision) ← transformer-2017(nlp_llm))**
→ 허용. 엣지는 그대로 걸고, flow chart에서는 점선 테두리의 ghost 노드로 렌더한다. ghost 노드 클릭 시 해당 노드의 상세로 이동.
→ 이유: 섹터 간 아이디어 전파야말로 이 사이트가 보여줘야 할 핵심 장면이다.

**§7. 계보의 뿌리가 2012 이전이다 (LSTM 1997 등)**
→ 엣지를 걸지 않는다. 2012 이전 배경은 홈의 프리퀄 정적 블록(최대 5개, 상세 페이지 없음)에서만 다루고, 해당 노드의 `background`격 서술(intro/mid의 도입부)에서 텍스트로 언급한다.
→ 이유: 타임라인 축은 2012에서 시작한다. 축 밖 노드는 레이아웃을 깨뜨린다.

**§8. 직접 계승이 3개 이상이다**
→ 가장 직접적인 2개만 엣지로 남긴다. 나머지는 텍스트로.
→ 이유: 가독성. validator가 `evolves_from` ≤2를 강제한다.

## C. 항목 자격

**§9. 논문이 없는 제품/모델이다 (ChatGPT, GPT-4, Sora, Cursor…)**
→ 허용. `type: "model" | "product"`, `link`는 공식 report/blog 또는 확실하지 않으면 `null`. 상세 본문에 반드시 다음 취지의 문구를 포함한다: "내부 구조는 비공개이며, 이하는 공개된 정보 기준의 설명이다." 메커니즘 설명은 공개적으로 알려진 기술 계보(예: ChatGPT → InstructGPT의 RLHF)로 한다.
→ 이유: 발전 흐름에서 제품 마일스톤을 빼면 이야기가 끊기지만, 비공개 내부를 아는 척해서는 안 된다.

**§10. 버전 시리즈를 다 넣을지 (DINOv1/2/3, GPT 계열…)**
→ PRD §5 시드 리스트에 있는 것은 전부 노드로 넣는다. tier로 구분한다: 패러다임을 바꾼 버전=major(풀 상세), 증분 개선=minor(변경점 중심 컴팩트 상세). 판정 기준: "이 노드를 빼면 발전 흐름 이해에 구멍이 나는가?"
→ 이유: 사용자 요구가 "계보 전체를 보고 발전 과정에서 아이디어를 얻는 것"이다. 단 모든 노드에 풀 분량을 강제하면 증분 버전 설명이 억지로 부풀어 질이 떨어진다.

**§11. 같은 아이디어를 담은 논문이 여러 개다 (DDPM vs score-based diffusion 등)**
→ canonical 논문 1개만 노드로 만들고, 형제 논문은 본문에서 저자·연도와 함께 언급한다.
→ 이유: 노드는 아이디어 단위이지 서지 목록이 아니다.

**§12. 2012 이전인데 꼭 필요한 배경이다 (퍼셉트론, 역전파, LSTM, ImageNet 데이터셋)**
→ 노드 금지. 홈 화면 프리퀄 블록(카드형 단문 최대 5개)으로만 다룬다.
→ 이유: §7과 동일.

## D. 날짜·사실

**§13. 발표 시점이 여러 개다 (arXiv 공개 vs 학회 발표 vs 서비스 출시)**
→ 논문은 arXiv v1 공개 시점, 제품/모델은 최초 일반 공개 시점. `date`는 월까지 확실할 때만 `YYYY-MM`, 아니면 `YYYY`. 월을 추측으로 채우지 않는다.
→ 이유: 일관된 축 + 날조 방지.

**§14. arXiv ID가 가물가물하다**
→ **절대 지어내지 않는다.** 확실하지 않으면 `link: null`로 두고 본문에 논문 제목만 쓴다. validator는 형식(`\d{4}.\d{4,5}`)만 검사할 수 있고 실존은 검증 못 하므로, 이 규칙은 전적으로 작성자의 정직에 달려 있다.
→ 이유: 틀린 링크는 없는 링크보다 나쁘다.

**§15. 파라미터 수·벤치마크 점수 같은 수치가 확실하지 않다**
→ 확실할 때만 쓴다. 아니면 정성 서술("수십억 파라미터 규모", "당시 최고 성능")로 대체한다. 수치 날조는 어떤 경우에도 금지.
→ 이유: 이 사이트의 신뢰성은 수치의 정확성이 아니라 정직성에서 나온다.

**§16. 2025~2026 항목은 지식이 얕을 수 있다**
→ 섹터당 최대 3개까지만 허용(PRD 시드 리스트가 이미 준수). 해당 노드는 `uncertainty`에 반드시 포함: "⚠ 2025년 이후 정보는 작성 시점 지식 기준으로, 세부 사항이 실제와 다를 수 있다."
→ 이유: 최신성은 필요하지만 불확실성은 표시되어야 한다.

**§17. 확신 3단계 (전역 규칙)**
→ 확실 = 단정 서술("~이다") / 개연 = 완곡 서술("~로 알려져 있다") / 불확실 = 생략하거나 `uncertainty`에 ⚠로.
→ 이유: 독자가 문장만 보고 신뢰 수준을 구분할 수 있어야 한다.

## E. 수준별 콘텐츠

**§18. intro에 수식을 조금만 쓰고 싶다**
→ 금지. intro에는 수식·그리스 문자·`<sub>/<sup>`가 들어갈 수 없다(validator 검사). 모든 비유는 직후에 "비유↔실제 대응"을 명시한다("비유에서 X는 실제로 Y에 해당한다"). 대응을 명시할 수 없는 비유는 삭제한다. 의인화 뭉뚱그리기("모델이 스스로 생각한다")는 대응 명시 없이는 금지.
→ 이유: 입문 레벨의 존재 이유. 틀린 비유는 없는 비유보다 해롭다.

**§19. deep을 쓰는데 mid 내용을 반복하게 된다**
→ 허용. 각 레벨은 다른 레벨을 읽지 않아도 완결되어야 하므로 중복 서술은 정상이다. 단 "중급에서 설명했듯"류의 레벨 간 참조는 금지.
→ 이유: 독자는 한 레벨만 읽는다.

**§20. 수식을 얼마나 쓸 수 있나**
→ deep에서만, 메커니즘 이해에 필수적인 1~3개. 표기는 Unicode 문자 + `<sub>/<sup>`만(LaTeX·렌더링 라이브러리 금지). 모든 기호는 첫 사용 시 본문에서 정의한다.
→ 이유: 오프라인 단일 파일 제약 + "수식은 수단이지 목적이 아니다".

**§21. minor 노드를 쓰다 보니 전 버전 설명을 다시 하게 된다**
→ 금지. minor의 각 레벨은 "전 버전 대비 무엇을·왜·어떻게 바꿨나"만 다룬다. 전 버전 내용이 필요하면 `<a href="#/item/이전id">` 링크로 대신한다. deep에는 변경된 메커니즘의 기술 상세가 반드시 포함되어야 한다.
→ 이유: 중복 제거 + 계보를 따라 읽는 독서 경험.

## F. 스타일·엔지니어링

**§22. 문체와 표기**
→ 한국어 평서문 "~다"체. 기술 용어는 첫 언급 시 한국어(English) 병기, 이후 한 표기로 통일. 논문 제목은 영어 원문 유지. 음슴체·구어체·이모지 금지(유일한 예외: `uncertainty` 안의 ⚠).
→ 이유: 문서 전체의 균질성.

**§23. 크기 예산**
→ 섹터 데이터 파일 각 ≤200KB, 리포의 사이트 파일 합계 ≤2.5MB, `dist/index_standalone.html` ≤2.5MB. 이미지는 인라인 SVG 외 금지.
→ 이유: file://로 즉시 열리는 단일 산출물이 목표다.

**§24. 내비게이션이 깨지는 상황**
→ 존재하지 않는 해시는 반드시 404 패널(홈 링크 포함)을 렌더한다(빈 화면 금지). 모든 상세 페이지에 "← flow chart로" 버튼. 브라우저 뒤로가기는 항상 동작. hover 전용 인터랙션 금지(모바일). 페이지 전체의 수평 스크롤은 금지하되 flow chart 컨테이너 내부의 가로 스크롤만 허용.
→ 이유: PRD §6~§8의 안전망.

**§26. 본문이 벽글이 된다 (가독성)**
→ 다음 세 가지를 validator가 강제한다. (1) `<p>` 하나는 태그 제거 후 **320자 이하** — 넘치면 문단을 나누거나 표·목록으로 옮긴다. (2) 한 문단 안에 줄표(—)를 2회 이상 쓰지 않는다 — "용어 — 정의 — " 식으로 정의를 문장 속에 욱여넣지 말고, 문장을 분리하거나 표로 뺀다. (3) major의 mid에는 `<table>`/`<ul>`/`<ol>` 구조 요소가 최소 1개 있어야 한다. 이와 별개로 셋 이상의 나열, 전/후·A/B 대비(CBOW vs Skip-gram 등), deep의 수식 기호 정의는 산문 대신 **표가 기본**이다(허용 태그: `table/thead/tbody/tr/th/td`, 속성 금지, 스타일은 css 담당).
→ 이유: 상세 본문의 기본 독서 모드는 훑어 읽기다. 정보 구조가 문장 안이 아니라 눈에 보여야 한다(사람 피드백 2026-08-01).

## G. 메타

**§25. POLICY가 다루지 않는 상황을 만났다**
→ (1) 보수적인 쪽을 선택한다 — 날조보다 생략, 추가보다 유지. (2) 선택과 근거를 IMPLEMENTATION_PLAN.md의 Log에 1줄 기록한다. (3) 사람의 답을 기다리며 멈추지 않는다.
→ 이유: 루프는 무인으로 완주해야 하고, 판단은 나중에 감사 가능해야 한다.
